# 收尾流程（wrapup）

按顺序执行以下步骤，全部完成后才算收尾结束。

## 1. 确定活跃功能

读 `context/features/ACTIVE` 得到功能名 `<feature>`，工作目录为 `context/features/<feature>/`。

## 2. 更新 status.md

- 先运行 `bash scripts/code-status.sh`（或复用本会话已有输出），**由 AI 总结**各端脏区、分支与活跃功能关联，再写入文档（禁止模板化空话）。
- 根据本次实际完成的工作，更新平台矩阵中对应格子（⬜ 未开始 / 🚧 进行中 / ✅ 完成 / ❌ 阻塞）。
- 更新「待办 / 阻塞」小节：完成的划掉或移除；新发现的问题追加，注明属于哪个端。
- 更新文件顶部的 `最后更新` 日期。
- 矩阵只反映事实，不要乐观标记：代码写完但没自测通过的算 🚧。

## 3. 视情况更新 impl-notes.md

满足以下任一条件时必须写/更新 `impl-notes.md`：

- 本次完成了 **web 端的接口联调**（这是其他三端移植的依据，最重要）；
- 本次在任何端发现了**契约文档没写的接口实际行为**（同时按契约规则更新 contracts）；
- 本次做出了会影响其他端实现的**逻辑决策**（状态流转变化、边界处理策略等）。

impl-notes 写法要求：**平台无关**。描述状态流转、接口调用时序、边界情况、错误处理策略、联调踩坑；不要出现 React/Kotlin/Swift 的具体 API 名。

## 4. 提交 context 仓库

在工作区根目录执行：

```bash
git add context/ CLAUDE.md .claude/ .cursor/ 2>/dev/null; git commit -m "docs(<feature>): <一句话概括本次进展>"
```

只提交编排仓库自身的文件；apps/ 下各仓库的代码提交由用户或独立流程决定，不要在这里顺手提交 apps。

## 5. 汇报

用 3-5 行向用户汇报：本次完成了什么、矩阵变化（哪几格更新）、遗留待办、下一步建议（例如"web 已联调完成，可以开始 /port ios"）。
