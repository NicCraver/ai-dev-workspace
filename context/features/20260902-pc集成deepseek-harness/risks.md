# 风险分析：PC 端内嵌 dsh 未来会踩的坑

> 2026-09-03 ｜ 基于本地实测，不是清单式猜测。每条标注**判据**（怎么确认）与**缓解**。
> 结论按「已实测确认」→「高」→「中」→「低」排列。

---

## 零、已实测确认的事实

先把已经量过的钉死，避免后面反复讨论。

### 0.1 Chromium 102 的特性缺口（**核心发现**）

扫了 `resources/dsh-runtime/app` 下全部 733 个 `.js/.mjs/.css`，dsh 用到而 Chromium 102 不支持的：

| 特性 | 需要 Chrome | 类型 | 现状 |
|---|---|---|---|
| `AbortSignal.timeout` | 103 | JS | ✅ 已 polyfill（就是你踩的那个） |
| `toReversed()` | 110 | JS | ✅ 已 polyfill |
| `AbortSignal.any` | 116 | JS | ✅ 已 polyfill |
| `Promise.withResolvers` | 119 | JS | ✅ 已 polyfill |
| `:has()` | 105 | **CSS** | ❌ **无法 polyfill** |
| `@container` | 105 | **CSS** | ❌ **无法 polyfill** |
| `color-mix()` | 111 | **CSS** | ❌ **无法 polyfill** |
| `subgrid` | 117 | **CSS** | ❌ **无法 polyfill** |
| `scrollend` | 114 | 事件 | ❌ 未处理 |

JS 那 4 个恰好被现有 preload 全覆盖——这就是现在「用起来问题不大」的原因。**剩下的是 CSS，见 §2.1。**

`showDirectoryPicker` **没有命中**：dsh 的目录选择不走 File System Access API，
所以此前担心的「Electron 19 对 FS Access 支持有限」这条**不成立**，可以划掉。

### 0.2 本地端口的访问控制（实测，修正此前判断）

起 dsh 后对监听端口做的探测：

| 探测 | 结果 | 含义 |
|---|---|---|
| 首页裸请求 | `200` | 本机任意进程可读首页 |
| `/api` 不带 Origin | `404` | 过了 fence（404 是路径本身不存在） |
| `/api` 带 `Origin: https://evil.example` | **`403`** | **browser-trust fence 生效** |
| `/api` 带合法 Origin | `404` | 未被 fence 拦 |
| 从 `192.168.x.x:<port>` 连 | `000` | **只绑回环，外网/局域网连不上** |

**修正**：spec 第五节原先写「本地端口是最大安全洞」，**说重了**。实测 fence 对跨站
Origin 返回 403，且只绑 127.0.0.1。真实风险等级见 §3.4，比原判断低。

## 一、高风险 · 会实际影响用户体验或上线

### 1.1 CSS 静默失效（**最该先看的一条**）

**为什么最严重**：JS 缺 API 会抛异常，你立刻能看见；**CSS 不支持的属性会被浏览器直接丢弃，不报错、不警告**。表现是布局错位、悬停态没反应、折叠区域高度算错、深色模式颜色不对——而且只在特定组件、特定状态下出现，测不全。

四个特性的典型后果：

| 特性 | 一般用来做什么 | 102 下会怎样 |
|---|---|---|
| `:has()` | 父元素按子元素状态变样式（「有选中项的行高亮」） | 选择器整条失效，**同一规则块里的其他样式一起丢** |
| `@container` | 容器查询，按容器宽度切布局 | 查询块内样式全不生效，永远是默认态 |
| `color-mix()` | 动态混色（悬停加深、禁用变淡） | 该颜色声明失效，回退到继承色或透明 |
| `subgrid` | 嵌套网格对齐列 | 退化成独立网格，**列错位** |

> `:has()` 的失效方式尤其阴险：CSS 规范规定选择器列表里有一个不认识的伪类，**整条规则作废**。所以不是「少个高亮」，可能是「这块的样式整体没了」。

**判据**：在 dsh 界面开 devtools → Elements → Styles，找带删除线/灰掉的声明；或
Console 里跑
`CSS.supports('selector(:has(a))')` / `CSS.supports('width','1cqw')` / `CSS.supports('color','color-mix(in srgb,red,blue)')`，Chromium 102 上全返回 `false`。

**缓解**（按代价排序）：
1. **接受**——先让业务方看实际界面，很多失效点在非关键路径上，不一定值得修。
2. **注入补丁 CSS**——在 preload 里插一段覆盖样式，把关键几处用 102 支持的写法重写。
   治标，且 dsh 升级后要重对。
3. **升 Electron**——根治。见 §1.4。

### 1.2 安装包体积与增量更新

产物 843MB，其中 dsh-runtime 417MB。dmg 压缩后大概 300-400MB。

**真正的坑不在首次安装，在更新**：本仓库有升级机制（`src/main/ipc/upgrade-ipc.js`）。
如果走的是**全量包替换**，那么以后每次发版——哪怕只改一行业务代码——用户都要重新下
几百 MB，其中 417MB 是一动没动的 dsh。

**判据**：读 `upgrade-ipc.js` 与服务端升级接口，确认是全量包还是差分。

**缓解**：
- 把 dsh runtime 从主包里拆出去，做成**首次点入口时按需下载**。安装包回到原来的
  ~425MB，更新包也不含 dsh。代价是要做下载进度、完整性校验、断点续传、离线降级。
- 若升级本来就是差分（bsdiff 类），417MB 的不变内容差分后接近 0，问题自动消失——
  **先查清楚这一点再决定要不要做上面那套**。

### 1.3 内网代理（内网部署几乎必踩）

dsh 跑在**独立 Node 子进程**里，**不继承 Electron 的代理设置**。公司网络若要求走代理
出网，dsh 连 `platform.deepseek.com` 会直接超时，表现为「模型没响应」，且错误信息大概率
不会明说是代理问题。

**判据**：在需要代理的网络里启动 dsh，随便发一条消息，看是否卡住/超时。

**缓解**：spawn 时把代理注入子进程环境——
`HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY`，取值可从 Electron 的
`session.defaultSession.resolveProxy()` 或系统设置读。这是 `dsh.controller.js` 里加几行的事，
但**必须在内网真环境验证**，因为 dsh 用的 HTTP 客户端是否认这几个环境变量还没确认。

### 1.4 Electron 19 是这一切的根

Chromium 102 的天花板（§1.1）、必须捆 129MB Node（Node 16 不够）——两个最大的成本都来自
Electron 19。

升到 Electron 30+ 可以**同时**解决：
- 渲染层到 Chromium 124+，CSS 缺口全部消失
- 内置 Node 20/22，`ELECTRON_RUN_AS_NODE` 直接复用，**省掉 129MB**

代价：Vue 2.7 + electron-vue 老脚手架 + `@electron/remote` + 两个原生模块，升级是独立工程。

**建议**：不要为 dsh 去升 Electron，但**把 dsh 的这两笔成本记进 Electron 升级的收益账**——
下次评估升级 ROI 时，这是实打实的两条。

## 二、中风险 · 会在特定条件下咬人

### 2.1 孤儿进程

`dsh.controller.js` 在 `before-quit` / `will-quit` / `process exit` 三处回收子进程。
但主进程被 `SIGKILL`（崩溃、强制退出、活动监视器强杀）时**来不及执行任何回调**，
dsh 进程会留下来，占着端口和约 185MB 内存，直到用户重启机器。

**判据**：`kill -9` 智信主进程，然后 `pgrep -f dsh-runtime/node/bin/node`。

**缓解**：启动时把 pid 写进 `userData/dsh.pid`；下次启动先读这个文件，若进程还活着且
确实是 dsh 就先杀掉。约 20 行。

### 2.2 Windows 完全没验证

macOS arm64 全链路通了，Windows **一次都没跑过**。可预见的三个问题：

1. **路径长度**。453 个包的 `node_modules` 嵌套深度 + 安装目录前缀，容易撞 Windows 的
   260 字符 `MAX_PATH`。npm 的扁平化通常够用，但 dsh 依赖里有
   `@deepseek-ai/dsh-client-ui-settings-plugin-inventory` 这种超长包名，风险不低。
2. **杀毒软件**。安装目录里躺着一个未签名的 `node.exe`，且它会被主程序 spawn 出来跑
   任意脚本——这是杀软的典型告警模式。企业统一管控的终端可能直接拦。
3. **代码签名**。本仓库有 Windows 签名证书，但 `afterPack` 拷进去的 `node.exe`
   在签名流程之后/之外，是否被一并签名要确认。

**判据**：在 Windows 上完整跑一遍 `prepare-dsh-runtime.js` + `pack:win-test`，装到一台
装了企业杀软的机器上。

### 2.3 dsh 升级的破坏性变更

已锁 `0.1.1-rc.2`。但官方明说 Developer Preview 会有 breaking change，且**不接受外部 PR**——
遇到问题只能自己打补丁或绕。

升级时至少要重验三处，它们都是我们依赖的**未公开约定**：

| 依赖点 | 位置 | 变了会怎样 |
|---|---|---|
| stdout 就绪行格式 `dsh web: http://127.0.0.1:<port>` | `dsh.controller.js` 的 `URL_PATTERN` | 正则匹配不上 → 90s 后超时报「启动失败」 |
| CLI 参数 `web --no-open --host --port` | 同上 | 参数改名 → 进程起不来 |
| `$DSH_HOME` 的语义与 profile 布局 | `resolveDshHome()` | seed 失败或读到旧结构 |

**缓解**：升级前先在 `/tmp` 单独装新版跑一遍上面三条；`URL_PATTERN` 可以放宽成
「匹配任意 `http://127.0.0.1:\d+`」（当前已经是这样，尚可）。

### 2.4 profile 漂移

`$DSH_HOME/profiles` 是**首次启动时** seed 的。dsh 升级后，用户机器上留着的是老 profile，
新版本的插件组合可能与之不兼容——表现为启动失败或功能诡异，而且**只在升级过的老用户身上出现**，
新装用户一切正常，最难排查的那类问题。

**缓解**：在 `userData` 里写一个 `dsh-version` 标记；启动时比对，版本变了就把
`$DSH_HOME/profiles` 重命名备份后重新 seed。

### 2.5 审批策略完全没锁

dsh 能跑 shell、能改文件，当前直接加载官方 UI，**没有做任何策略锁定**。

具体要处理的：
- 会话默认 `workspace-write`，cwd 必须是用户显式选的工作区，**不能是主目录**
- `danger-full-access` 会同时关掉沙箱和提示，应在配置层禁用、不给 UI 开关
- 「Always allow (this session)」会把该会话的审批策略降成 `never`，之后不再询问——
  这个按钮给不给用户，是产品决策

**这不是「dsh 不安全」，而是「我们没配」**——它自带了这套机制，只是默认值偏向开发者便利。

## 三、低风险 / 已知限制 / 待观察

### 3.1 首次使用要填 API key

用户点进去看到的是 dsh 的设置页要 key，不知道去哪拿。需要企业侧的统一配置下发，
或至少在面板上加一句引导。

### 3.2 `dsh plugin` 不可用

该子命令把参数转发给 pnpm，用户机器上没有 pnpm。插件市场这条路在内嵌形态下走不通。

### 3.3 可观测性

dsh 崩了用户只看到面板报错。日志有 `[dsh]` 前缀写进应用日志，但用户不会主动去看。
崩溃后也没有自动重启（只有手动「重试」按钮）。

### 3.4 本地端口的真实风险等级

实测（§0.2）：只绑回环、跨站 Origin 被 403 拦。

剩余风险两条，都不高但值得知道：
- **不带 Origin 的本机请求能过 fence**。但发起这种请求的进程本来就以同一用户权限运行，
  自己就能跑 shell——**不构成提权**。
- 不带 Origin 的跨站请求（`<img>`、`<form>` 提交）能绕过 Origin 检查。仅当 dsh 存在
  「GET 即产生副作用」的端点才可利用。**没有验证过**，属于待确认项而非已知漏洞。

### 3.5 数据出境

代码和文件内容会发给模型。走公网 DeepSeek 就是出内网，这是合规问题不是技术问题，
需要法务与安全过。走内网 OpenAI 兼容端点则无此问题。

## 四、建议的处理顺序

1. **先看 CSS 实际坏成什么样**（§1.1）——开 devtools 扫一遍 dsh 界面。这决定后面所有投入
   值不值。如果界面基本能用，其余都是可控工程问题。
2. **查清升级是全量还是差分**（§1.2）——决定要不要做按需下载那套。
3. **内网代理注入**（§1.3）——几行代码，但不做的话内网直接用不了。
4. **锁审批策略**（§2.5）——上线前的硬门槛。
5. 孤儿进程兜底（§2.1）、profile 版本标记（§2.4）——各约 20 行，顺手做掉。
6. Windows 全链路验证（§2.2）——如果目标平台包含 Windows，这是独立一轮工作。

体积裁剪（275MB 里约 120-150MB 用不上）我**不建议现在做**：Cordis 是运行时动态装载插件，
盲裁容易在某条冷路径上炸，而且省下的量还不如「按需下载」方案彻底。
