# 实现笔记：已读水位兜底

> 平台无关的逻辑提炼，供安卓 / iOS 后续对齐时参考。本轮只实现了 PC（`apps/desktop`）。
> 设计见 `spec.md`，实施步骤见 `plan.md`，各任务与评审记录见 `status.md`。
> **2026-08-26 真机验收全部通过**，验收方式与实证日志见 `status.md`。

## 一、为什么需要这一层

IM 厂商（融云）的回执消息在 adapter 属性表里是 `isPersited: false`：

```
"RC:ReadNtf"  :{isCounted:!1, isPersited:!1}
"RC:RRReqMsg" :{isCounted:!1, isPersited:!1}
"RC:RRRspMsg" :{isCounted:!1, isPersited:!1}
```

**不落库、不进历史。** 客户端那一刻不在线，回执就永久丢失，之后拉多少次历史都补不回来。
丢不丢全看时机——这就是「已读不翻转」无法稳定复现的根本原因。

上一轮（`20260824-3端-私聊群聊已读回执不翻转排查`）试图在推送通道上打补丁，18 个 commit 后
确认那是天花板。**已读应该建立在可靠通道上，而不是修补不可靠通道。**

## 二、核心概念：已读水位

> **`水位[U] = T`** 表示「U 在 T 时刻确实打开着这个会话」。
> 于是我发的任何 `sentTime <= T` 的消息，对 U 已读。

像一条水平线画在消息列表上：线以下（更早）的算已读，线以上（更晚）的不算。

### 三个证据源

都走 `isPersited: true` 的可靠通道，与回执通道的失效条件**完全不相关**：

| 源 | 推出的水位 |
|---|---|
| 对方**发言** | 他那条消息的 `sentTime`（发言必然先打开会话） |
| 对方**表态** | **被表态那条消息**的 `sentTime` |
| 对方**引用回复** | **被回复那条消息**的 `sentTime` |

表态与回复在智信里走**同一条通道**（IM 消息扩展），数据结构完全一致
（`{ prefix: [{ s: 账号Id, t: 时间戳 }] }`，表态 prefix 是 emoji、回复是 `referInfo`），
所以代码上是同一段逻辑，不需要按前缀分支。

### 关键设计决策：水位取 `sentTime`，不取动作时间 `t`

取 `t`（动作发生时刻）覆盖面更大，但会多盖一段——从被作用消息到动作时刻之间的消息，
可能在对方视口下方，没真看到。取 `sentTime` 更保守：对方渲染到了那条消息，它前面的消息就在它上方。

**附带好处**：上一轮踩过「扩展条目缺 `t` 时用 1 占位」的坑，本方案结构上绕开了——根本不读 `t`。

> **权衡尚未定论**：对方翻历史给老消息表态时，他**此刻**确实打开着会话，按 `t` 能推出
> 「我发的所有消息都被看到了」；按 `sentTime` 只能推出一个老时间，等于白收一条证据。
> 要滚到历史里通常得先经过最新一屏，所以实测中对方极可能已看过最新消息。
> **放宽到 `t` 是产品判断，本轮保持保守档。**

### 两条不变式

1. **单调只增** —— 任何证据只把线往上抬，绝不下调。已显示已读的消息不会退回未读。
2. **只补不覆盖** —— 本地回执 / 服务端记录若已给出时间，**优先用它们**，水位只在它们都没值时兜底。
   理由：水位是下界，不如回执精确。

## 三、必须踩过才知道的坑

### 1. 会话 key 必须含**自己的账号 Id**（否则会产出错误已读）

水位表若按 `${会话类型}_${对端Id}` 做 key，切换账号时会串：

- PC 「切换账号」通常**不重载渲染进程**（智信 PC 端全仓库无一处 `location.reload()`）
- 模块级的水位表跨账号存活
- 账号 A 与 U 私聊留下 `1_U`，切到账号 B 后 key 还是 `1_U` → **A 的水位套到 B 头上**

正确做法：`${自己账号Id}_${会话类型}_${对端Id}`，`targetId` 或 `selfId` 缺任一时返回空串（调用方据此清空）。
群聊不受影响（「U 打开着群 G」这个断言与登录者无关），**只有私聊会错**。

> 这是整个方案里唯一一条会**产出错误已读**的路径，务必在各端都堵上。
> PC 真机已验证：切账号后新账号水位为空，所有消息判未读，无一条串过去。

### 2. 「本地消息」标记的真实语义（智信 PC 端特有，各端需自查同类标记）

PC 端 `MessageModel.convertHitoryMessage` 对**每一条**从公司 chat 服务拉回的历史消息
无条件写 `isLocalMessage = true`，而同一个函数又把这些消息的扩展塞进了全局扩展表。

**`isLocalMessage` 的真实语义是「IM 厂商本地库里没有这条消息」，不是「本地伪造的假消息」。**
它在本仓库的唯一其它用途是排除**发回执**的消息（SDK 没法为本地库里不存在的消息发回执）。

**读水位不发任何东西，这个约束对水位模块不成立。**
把它当排除项写进证据收集，会把整类服务端历史消息的表态/回复证据白白扔掉——
而融云返回条数不足时就会从 chat 服务补数据，短会话高频走这条路。

现在的处理：只在「对方发言」这一源上跳过（发言证据依赖消息本身可信度），
**表态/回复放行**（扩展数据来自服务端，与该标记无关）。

### 3. 证据只能来自「已加载的消息列表」

水位靠遍历当前已加载的消息算出来。对方给一条**未加载的**历史消息表态时：
扩展数据到了、全局扩展表里也有，但因为没遍历到那条消息，**收集不到**。

**功能上无损失**：消息从最新往回连续加载，被表态的消息比已加载区间还老，
则比它更早的消息也全部未加载——水位能影响的那些消息一条都不在屏幕上，算出来也没有任何显示会变。
滚动加载到那条消息后，拉历史会把扩展带回来，水位立刻算上。

**但验收方法受影响**：不能用「翻历史表态」验证功能，必须对**当前屏幕上可见的消息**表态。

### 4. 证据来源与会话 key 必须同源同步（终审查出，各端未必免费拿到）

水位表按会话 key 分桶，而证据来自「当前已加载的消息列表」。
**这两者必须由同一个「当前会话」派生**，否则会出现「新 key 配旧消息」的时序窗口——
把群里的发言证据算进私聊的水位，产出错误已读。

PC 端是**免费**拿到这个保障的：`messageList` 与 `conversationKey` 都是 lazy computed，
且都从 `OpenDialog.id` 派生，任一 watcher 触发时读另一个都会即时重算。
最坏情况是拿到空列表（贡献 `{}`，无污染）。

**其它端未必有同样的结构性保障。** 若消息列表与会话标识分别持有、异步更新，
必须显式校验「这批消息属于这个会话」再喂进水位，否则这是第二条会产出错误已读的路径。

### 5. 群聊只补分子，不改分母

群聊已读名单 `{ userId: 0 | 已读时间 }` 的成员由**发送方登记的 @ 名单**决定。
水位只把名单里已有的人从 `0` 翻成时间戳，**绝不新增成员**——
分母的语义是「需要已读的人数」，不该被旁人的表态改写。

实现上：合并结果的 key 集合恒等于本地名单的 key 集合。
另外要区分「本地未登记」（返回 `null`，调用方据此不渲染已读区块）与
「登记了但名单为空」（返回 `{}`，合法状态）——混为一谈会让每条别人发的 @ 消息都误显示成已读。

### 6. 渲染层的引用稳定性（Vue 2 具体，概念各端通用）

合并后的名单对象若在模板里逐条消息现算、每次返回**新对象**，会让监听该 prop 的子组件
每次重渲染都判定「变了」，进而强制整条消息的视图重建。

解法：按消息 Id 做**引用缓存**——值真变了才换新对象，没变就复用上一次的引用。
比较用「键集合 + 取值」的浅比较即可。

同理，水位表本身赋值给视图状态时也要比对，值没变就别换引用，
否则一次事件会连锁触发多轮无谓重算。

> 各端对应物：Android 的 `DiffUtil`/`RecyclerView` 复用、iOS 的 `UITableView` cell 复用，
> 判等口径不对同样会造成整条重建。

## 四、可观测是刚需，不是锦上添花

上一轮排查最大的成本来自：**用户报问题 → 拿不到现场 → 只能读代码推断**。

本轮加了一套验收日志（`readWatermarkDebug.js`）。**已决定长期保留**——
上一轮的教训就是没有它，所以按生产代码维护而不是用完即弃的脚手架。把三件事分开报：

1. **收到了哪些证据** —— 谁、什么时刻、来自哪个源、哪条消息
2. **当前水位是什么** —— 会话级按人
3. **每条消息的已读判定用了哪个源** —— 本地 / 服务端 / **水位** / 仍未读

第 3 条是关键：**即使回执通道正常、水位没被用上，也把水位那一列打出来**——
一次正常测试就能同时确认「水位算对了」和「当前是谁在起作用」，不必构造离线场景。

三条日志设计上的教训：

- **时间必须带日期**。只打时分秒的话，跨天消息看不出先后，
  「发于 16:45:43 / 水位 11:42:18 判已读」这种行会被误读成 bug。
- **去重要按「证据身份」（谁+哪条消息+哪个源），不能按「水位值」**。
  按值去重会把「低于当前水位」的证据完全静默，于是「收到了但没抬高」和「压根没收到」
  输出一模一样，没法排查。
- **「收到但未抬高」必须单独报一行**。这是最容易被误判成「功能坏了」的情形。
- **别指望生产包把日志函数体 DCE 掉**。原以为 `enabled` 为 `false` 时 Terser 能把
  整段函数体连同调用点一起删掉，实测不成立：`enabled` 是可变对象属性
  （`window.__readWatermark.enabled=false` 这个用法要求它可变），Terser 无法证明它恒为
  `false`，函数体一行不少地留在产物里。结论：热点调用点必须自己用
  `isWatermarkDebugOn()` 加门，不能指望关闭开关就等于零开销。

安卓 / iOS 若后续对齐，建议同样把这三类输出做出来，并注意上面这条 DCE 的坑。

## 五、验收方法（各端通用）

**原来那套「先确认显示未读，再触发证据」构造不出来**：对方在手机上打开会话去表态时，
会话打开本身就发了一条正常回执，本端在线就收到了，已读通过正常通道就翻了——
分不清是水位兜底生效还是回执本来就好使。

**改为看日志**：本端 @ 某人，那人用另一台设备表态 / 发消息，本端看日志的「来源」那一列。

若一定要验「回执丢失时水位顶上」，唯一构造方式是让本端在回执到达那一刻离线：
发消息 → **完全退出应用** → 对方表态 → 重开应用。
（实测中不必这么做——历史上早已丢失回执的老消息天然就是这个状态。）

**五条回归项**：群聊兜底 / 群聊分母不变 / 切账号不串 / 引用缓存不失效 / 只增不减。
