# Impl Notes：数据范围选择周工作

> 平台无关的实现笔记，是其他端移植的唯一逻辑依据。
> 本功能三端都内嵌 web 页，不做原生选择器；这里的笔记服务于 web 自身与后续接手的人。

## 四个子 tab 的形态

| tab | 数据 | 渲染 | 胶囊 |
|---|---|---|---|
| 全部 | `allTree` | 树 | 全部 / 团队 / 人员 |
| 关注 | `attentionTree`（后端就是平的） | 扁平列表 | 团队 / 人员 |
| 所属 | `belongTree`（树，按 `belong` 裁剪） | 树 | 全部 / 团队 / 人员 |
| 主管 | `manageTree`（树，按 `manage` 裁剪） | 树 | 全部 / 团队 / 人员 |

三个树 tab 共用同一套渲染与勾选逻辑（展开、胶囊过滤、半选、含团队工作、联动），
差别只在喂哪棵树。

## 状态流转

周工作面板只有三态：**取数中 → 有数据 / 失败**。

- 面板挂载即取数（一级 tab 切到「周工作」才挂载，不进入不请求）
- `accountId` 缺失时直接进失败态，文案「accountId 未就绪」，不发请求
- 取数成功后，一级 tab（全部 / 关注 / 所属 / 主管）之间切换**不再请求**，四棵树来自同一次返回
- 选中态与取数完全独立：树重载不清选中，选中只由外部传入的记忆回显与用户操作决定

## 接口调用时序

1. 打开数据范围面板 → 只有点「周工作」一级 tab 才挂载周工作面板
2. 挂载时一次性取四棵树（全部 / 关注 / 所属 / 主管），不按 tab 分次取
3. 保存时不单独提交周工作，与知识聊天的选中合并成一份提交

## 后端字段 → 前端节点（适配层的全部规则）

后端一套字段，界面另一套；中间隔一层适配，界面不认后端字段。

| 后端 | 前端节点 |
|---|---|
| 企业 `corpId` / `corpShortName`(缺则 `corpName`) | 团队节点，仅 `multiCorp=true` 时渲染这一层 |
| 一级板块 `plateId` / `plateName` / `childUnitList` | 团队节点 |
| 子节点 `id` / `title` / `childUnitList` | 团队节点 |
| 子节点 `person=true` + `userInfo{id,nickName,avatar}` | 人员节点，id 取 `userInfo.id` |
| `enableState=1` | 该团队多一条「含团队工作」可勾项 |
| `peopleCount` | 团队行右侧人数（人员固定 1） |
| `orphanUserList` | 未归属任何板块的关注人，挂在企业层下 |

三条容易踩的：

1. **一级板块与子节点字段名不同**（`plateId/plateName` vs `id/title`），必须分开映射，不能当同一种节点处理。
2. **`multiCorp=false` 时不要渲染企业层**，直接把第一家企业的板块与孤儿人员摊到第一层；否则单企业用户会多看到一层没意义的根。
3. **只有关注树是平铺的**（后端直接给 unitList，没有企业/板块层，界面就是一个扁平列表）。
   **所属 / 主管与全部同形**（企业 → `corpPlateList` → `childUnitList` 递归），界面也照树渲染，
   不要摊平——2026-09-04 实测：belongTree 最大层深 4、manageTree 3，摊平会丢层级。
   所属/主管的树要**按关系标记裁剪**：节点自己 `belong` / `manage` 为 true 就留；
   自己为 false 但子孙里有 true 的，当层级壳留；两头都不沾整枝丢
   （企业层没有这两个标记，永远走「壳」这条，空企业自然被丢掉）。

## 节点身份与选中 key 必须分开

- **选中 key 用后端原始 id**（`ww_{类型}_{原始id}`），要原样回传保存接口
- **行标识另用「类型:id」**，因为企业 / 板块 / 部门的 id 来自不同表，**会撞号**；用 id 当行 key 会导致展开一个部门时另一个同号板块跟着展开、或搜索时祖先链找错

移植到其他端时同样要区分这两者。

## 行的视觉与交互口径（2026-09-03 按设计稿定）

- **图标**：企业行用通讯录企业图标（与组织架构公司行同一张）；
  有团队报告 → 蓝色报告图标；没有 → 蓝灰层叠图标。人员走头像。
- **行尾数字 = 这一行在当前胶囊下能勾到的条目数**，随胶囊换口径（2026-09-04 定）：

  | 胶囊 | 数字 | 来源 |
  |---|---|---|
  | 全部 | 范围数 = 人 + 子树团队工作份数 | 后端 `countNumber` |
  | 团队 | 子树里的团队工作份数（含自身那份） | 前端数 `hasTeamWork` 节点 |
  | 人员 | 子树人数 | 后端 `peopleCount`，缺则前端数 |

  实测印证口径：`countNumber` 恰好 = `peopleCount` + 子树团队工作数
  （美腾 41 = 35 + 6，矿业研究设计院 14 = 11 + 3，全量核对无误）。
  团队胶囊下不能再显示 41 那种混合数——那 41 里有 35 个人，这个胶囊一个都勾不到。
  团队胶囊各顶层行数字相加 = 胶囊「团队 N」，两处同源。
- **胶囊计数**：「团队」只数有团队报告的节点（层级容器不算），于是「全部」= 团队 + 人员，
  与后端范围数口径一致。
- **三个胶囊都画半选**（2026-09-04 修正，推翻「半选只在全部胶囊」那条）。
  当初禁掉是因为勾选口径不分维，团队胶囊里的半选表达的是「人还没勾全」，而人员行根本不可见。
  现在口径已按胶囊分维（见下条），半选表达的就是「当前这一维里还有没勾的」，
  与眼前的行对得上，该画。
- **勾选口径随胶囊只看一维**（2026-09-04 补）。同一个部门行，三个胶囊下算法不同：
  | 胶囊 | 该行「全选」的判据 | 勾整行会写什么 |
  |---|---|---|
  | 全部 | 子孙人员全选 **且** 子树里每份团队工作都勾 | 人员 key + 板块 key + 标记 3、4 |
  | 团队 | 只看子树里的团队工作（含自身那份）都勾上 | 板块 key + 标记 4（**不碰人员**） |
  | 人员 | 只看子孙人员都勾上，团队工作不参与 | 人员 key + 标记 3（**不碰板块**） |
  理由：团队胶囊下人员行根本不显示，若仍要求人选齐，团队行永远勾不满、也永远显示未选。
  副作用（已知、可接受）：团队胶囊下，没有团队工作的部门（纯层级容器且子树里也没有团队工作）
  点勾选框无反应——这一维下它确实没有可勾的东西。叶子部门的行勾选框与右侧「含团队工作」
  在团队胶囊下会同步变化，是同一份数据的两个入口。
- **部门联动标记按维度给**：有人才写 type 3（部门联动人），有团队工作才写 type 4（部门联动板块）。
  以前不论哪个胶囊都只写 type 3，团队胶囊下会写出「选了 0 个人的联动人标记」。
- **胶囊也过滤行本身**（2026-09-04 补）。团队胶囊只留**开了独立汇报**（`enableState=1`）的组织；
  自己没开、但子孙里有开的，作为**层级壳**保留（否则子节点没处挂）；两头都不沾的直接不显示。
  人员胶囊同理：只留人员，以及子孙里有人的组织。
  这条与上一条配合才自洽——过滤前团队胶囊会列出一堆勾不动的纯容器行。
  **展开图标也随之判断**：当前胶囊下展开是空的就不给图标（例：某部门子级只有人和没开汇报的组，
  团队胶囊下它就是叶子）。模型里是 `hasVisibleDescendants(node, kind)`。
- **树展开**：全部 tab 有子节点的团队行尾显示收起/展开图标（与收纳组同一套 pack/unfold）；
  **点整行 = 展开/收起，点勾选框 = 选中**。人员行与关注/所属/主管三个扁平 tab 不显示该图标，点整行选中。
  展开/收起不要让列表滚回顶：虚拟列表的 reset 只跟切 tab / 胶囊 / 搜索走，不要跟展开集合。
- 「含团队工作」只出现在有团队报告的团队行右侧，且人员胶囊下不显示。
- **人员行只显示 nickName**，不带企业名、也不带上级部门名。层级靠缩进。

## 统一搜索与已选区（2026-09-03 按设计稿）

**搜索**：知识聊天那个搜索框同时搜周工作，结果分类为 全部 / 群组 / 人员 / **团队工作** / **人员工作**，
后两个排在群组人员之后；「全部」里周工作命中也排在群组人员后面。
搜索命中的周工作项勾选后与树里勾选写同一套选中集合。

**这两个 tab 搜不到也要显示**（2026-09-04 改，推翻「无命中不出现」）：tab 条不随关键字增减，
点进去看到空态即可——否则用户会以为周工作压根没参与搜索。判据改成「本入口带不带周工作候选」
（`weekWorkTeams` / `weekWorkPeople` 非空），不是「当前关键字有没有命中」；
不带候选的入口（选择 AI 框那类）照旧只有三个 tab。
一条都没搜到时 tab 条也保留（以前整条藏起来）。

> 四棵树因此要提到比面板更高的层级（web 放在 useDataRangePicker），
> 搜索与面板共用同一份、只取一次；取数时机是「切到周工作 tab」或「聚焦搜索」，都不进就不请求。

**周工作面板里的搜索就是同一个搜索**（2026-09-04）。它原来有个自己的输入框做树内行内过滤，
两套搜索行为不一致（一个过滤主列表、一个开结果面板）。现在周工作面板不再自带搜索：
搜索框由外层塞进它的子 tab 行（web 是 `#search` 插槽 + `DataRangeSearchEntry`），
两个一级 tab 用的是**同一个组件、同一份候选、同一套结果分类**。
随之而来的口径：**周工作主列表也不再随关键字过滤**——关键字只影响结果面板，
与知识聊天那边完全一致。移动端同理，两个 tab 都是点搜索按钮铺开整屏搜索层。

**已选区**：分 人员 / 群组 / 团队工作 / 人员工作 四组，每组一个标题带计数，空组不显示。
顶部四个 tab 是**锚点**——点了滚到对应分组，滚动时高亮跟着走，**不是过滤**。

**文案**：团队叫「XX团队工作」，人叫「XX周工作」。后缀由展示层按分组拼，
存进选中记录的是原名，避免出现「信息技术部团队工作团队工作」。

## 保存（点确定要给后端什么）

接口 `POST /agentSetDataRangeExpand/saveDataRange`，**全量写**——周工作字段少传就等于清空。

**`weekWorkScopeList`**：

| scopeDataType | 含义 | scopeDataId | childScopeDataIdSet |
|---|---|---|---|
| 1 | 个人 | 人员 id | 不带 |
| 2 | 板块（一份团队工作） | 板块 id | 不带 |
| 3 / 4 | **全部** tab 选中的部门（3 联动子级人员、4 联动子级板块） | 板块 id | 3=子级人员 id；4=子级板块 id |
| 5 / 6 | **所属** tab 选中的部门 | 板块 id | 同上 |
| 7 / 8 | **主管** tab 选中的部门 | 板块 id | 同上 |

要点：

- **联动记录不是「在哪个 tab 点的」，而是「在哪棵树里被选满」**（2026-09-04 修正）。
  四个 tab 共用同一份选中集合，同一个部门可能同时出现在全部/所属/主管三棵树里 ——
  在「全部」里全选，所属/主管里的部门当然也被选满了，就该同时产出 3/4、5/6、7/8 三组。
  所以**选中集合里只存 1（人）和 2（团队工作）两种 key**，3-8 在保存时按选中态回推。
- **每一层都发**：嵌套部门只要这一维被选满，父、子各出一条。
- 判据分两维、互相独立：子孙人员全选 → 出奇数那条；子树里的团队工作（含自身那份）全选 → 出偶数那条。
- **子级取整棵子树**（不是直接子级）；偶数那条的子集不含自己。
- **企业层不产出记录**：`scopeDataId` 要的是板块 id，企业只是层级壳。
- 关注 tab 没有部门层，只产出 1 / 2 —— 它列表里的**团队项必须按 type 2 落 key**。
  落成 3-8 那类会被保存逻辑跳过（那类是回推出来的，不从选中集合读），等于静默丢选择。
- **八个全选标记** = 四个 tab（全部/关注/所属/主管）× 两个维度（人/板块），全勾为 1，空集合算 0。
  所属/主管/关注的人与板块都是「全部」的子集，所以在全部里全选后这六个标记会自然变 1，不用特判。

**三态**（与知识聊天那三个 flag 同样的规矩）：用户没进周工作 tab、或取树失败时，
提交的周工作字段必须是「未知」，由保存层**原样透传记忆**，绝不能拿空集合覆盖。

## 保存后再打开的回显

后端**会把已被某条部门联动覆盖的人吃掉**：我们发 5 条（type 5、6、1、1、2）回来只剩 3 条
（5、6、2），两条 type 1 并进了 type 5 的 `childScopeDataIdSet`。
所以回显时**必须把 3-8 的 `childScopeDataIdSet` 展开成人员/板块 key**（奇数展人、偶数展板块），
否则那些人算没勾，行显示成半选。

## 边界情况

| 场景 | 预期行为 |
|---|---|
| `accountId` 未就绪 | 不请求，面板显示「accountId 未就绪」 |
| 接口失败 / 未部署 | 面板显示「周工作数据加载失败」，不回退假数据 |
| 四棵树中某棵为空 | 该 tab 显示空列表，其余 tab 正常 |
| 树全空 | 不显示表头「全部」勾选行（避免勾一个空集合） |
| 人员节点缺 `userInfo` | 用节点自身 `id` 与 `title` 兜底 |
| 后端没给 `team` / `person` 标记 | 按 `dataCode=teamWork_member` 且带 `userInfo` 判为人员，其余判团队 |

## 错误处理策略

取数失败不弹窗、不阻断整个数据范围面板 —— 知识聊天那半边照常可用，只有周工作面板显示失败文案。失败不自动重试；关掉面板再进来会重新取。

## 联调坑（实际接口 ≠ 文档之处）

- **2026-09-03：后端最初给的路径是错的。** 文档写的 `/corpPlateAccountRel/weekWorkDataRangeTree`
  在测试环境 192.168.10.25 上五个网关前缀（`/api/aiBasic`、`/api/contact/v1`、`/api/chat/v1`、
  `/aiChatApi`、`/api`）全部 404，`apps/contact` 仓库里也搜不到该接口。
  后端确认真实路径是 **`/personalAiFrame/weekWorkDataRangeTree`**，服务仍是 aiBasic
  （前缀 `/api/aiBasic`）。契约与代码已更正。
  > 中途一度怀疑是前缀问题：行动中心（zx-operation-center）的 `corpPlateAccountRel/*`
  > 那一族接口确实走 `/api/actionCenter/v1`，但本接口不属于那一族，是 AI 框自己的接口。
- **2026-09-03 首次联调，实际回参与文档差四处**（accountId=1880150187008081921，corpId=6，测试环境 192.168.10.25）。契约已按实际更正：
  1. **回参包了两层** `{code,msg,data:{code,msg,data:{业务}}}`。web 的拦截器只解一层，
     取数函数里必须再剥一层，否则适配层收到的是包裹对象，四棵树全空、面板一片空白 ——
     **最坑的一条，不看回参根本发现不了**。
  2. **`dataCode` 不能用来判节点类型**。实际取值是 `own_my_team` /
     `own_my_attention_team_unit` / `own_attention_user_unit`（不是文档写的
     `teamWork_plate` / `teamWork_member`），且同一个值团队和人员都在用。
     判类型只能看 `team` / `person`（实测 26 个节点全都带，可靠）。
  3. **`userInfo.accountId` 恒为 null**，人员的 accountId 在**节点自身的 `id`** 上；
     `userInfo` 里只有 `nickName` / `avatar` 可用。
  4. **所属 / 主管树里有空壳板块**（该关系为 false、`childUnitList` 为空），只是层级占位。
     不按 `belong` / `manage` 过滤的话，所属 tab 会多出「人力资源部」「运维部」两个点不动的空条目。
- **id 跨类型撞号已被实测证实**：真实数据里有 4 组，板块与其同名子团队用同一个 id
  （如「前端开发组」的 id 等于 plateId）。这正是行标识必须用「类型:id」的原因。
- 调接口需要 `clientType` 头（值取会话里的 `clientType`，如 `app`），缺了会返回
  `G_C_003 客户端类型不能为空`，而不是 401/404，容易误判成路径问题。

## 与 bridge 的交互

周工作面板本身不与原生通信。整个数据范围页的宿主通信（token 获取、保存后回传）沿用
`/m/data-range`、`/zx/data-range` 两个入口页的既有协议，见 `context/bridge.md`。
