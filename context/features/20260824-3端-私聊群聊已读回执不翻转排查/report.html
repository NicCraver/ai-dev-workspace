消息已读回执异常 · 三端链路排查汇报

2026-08-24 纯代码审计 · 未改任何代码 desktop / android / ios 1d79054

问题最集中在 PC 端（apps/desktop）。

PC 是三端里唯一不用融云 SDK 原生回执 API 的一端——发送方登记、阅读方回执、回执入库全是自研。自研实现与 SDK 原生在四个地方口径不一致，每一处都能单独造成「对方看了、发送方仍显示未读」。

私聊 9 格、群聊 9 格两张组合推演表，断点的交集只有一个位置：PC。与「私聊、群聊均有」的反馈吻合。

背景与约束

  • 现象无法稳定复现，用户遇到时未记录，也说不清是哪一端发的消息 → 没有复现路径，唯一证据是代码本身。
  • web 端不参与 IM 已读回执（grep 命中的全是个人 AI 框语境的 unread），所以是「3 端」而非 4 端。
  • 本轮只查「已读回执」，不含「自己的未读数 / 红点多端同步」。

机制总览：两套完全独立的通道

私聊群聊（@ 消息）
主通道 融云 RC:ReadNtf，带 lastMessageSendTime，覆盖该时间之前全部消息 融云 RC:RRReqMsg（发送方要求回执）→ RC:RRRspMsg（阅读方响应）
服务端旁路 datasyn/readMessage 写 · datasyn/getReadMessage 读 无。服务端没有群维度按人已读接口，群「已读 N 人」只有融云一条路

ReadLastMessage 有 6 个调用点（:871,1246,1334,1352,1366,2320），但每一个都先撞这两行。isFirstScreen 在向上翻历史时置 false，showDownMsg 是「下方有新消息」提示。

安卓进会话就无条件发（ConversationFragment.java:1393），iOS viewWillAppear 就发（ZXRCIMBaseChatController.m:151）——两端都没有等价门槛。

滚回底部时 isFirstScreen 的 watcher 会补一次，所以不是必然失败，而是取决于用户当时滚到哪——这正是「偶发、说不清条件」的形状。

必须说清的限制

  1. 全部结论未经真机验证。A 级也只是「代码上必然」。
  2. SDK 可读性三端不对等。PC 的 adapter 是明文 JS，涉及 SDK 内部的结论逐条复核过；iOS 只读了公开头文件与调用层；安卓只有 jar + libRongIMLib.so，内部完全不可读——凡涉及原生 SDK 内部的推断一律压到 B 级。
  3. 未覆盖会话列表未读数 / 红点（本轮范围外）。
  4. datasyn/getReadMessage 在 context/contracts/ 下无契约文件，三端都在调，本次未逐字段比对。
