# 实现笔记：已读回执

> 平台无关的逻辑提炼，供安卓 / iOS 后续对齐时参考。本轮只实现了 PC（`apps/desktop`）。
> 代码事实与行号见 `findings.md`，实施步骤见 `plan.md`，验收见 `acceptance.md`。

## 一、已读状态的两条不变式

这是本轮设计的核心，**与平台无关**，任何端重构已读逻辑都应遵守：

**1. 单调性** —— 已读只增不减。
任何数据源报了已读，就不能因为另一个源没有记录、或本地缓存过期丢失，而回退成未读。
实现上体现为：合并时一律取 `max`，不做覆盖赋值。

**2. 多源合并** —— 已读时间来自多个彼此独立的源，取最大值。
关键点是**各源之间不能有依赖关系**。PC 原实现的 bug 正是把服务端兜底写成了

```js
serverTime = localCache[date] && serverMap[messageUId];
```

服务端数据被本地缓存的存在性挡住了——本地缓存整片缺失时，服务端明明有数据也取不到。

## 二、已读的三个数据源（按可靠性排序）

| 源 | 覆盖面 | 生命周期 | 备注 |
|---|---|---|---|
| **表态 / 回复反推** | 只覆盖被表态或回复过的消息 | 与消息扩展同寿 | 最可靠——动作本身证明看过，完全不经过回执通道 |
| **服务端已读接口** | 全量 | 服务端保留期 | 唯一可跨设备重建的源 |
| **IM 厂商回执** | 受窗口期限制 | 融云默认 1 天、上限 15 天 | 会被 SDK 的本机记录过滤掉 |

**结论：表态/回复反推应该作为独立的兜底层实现**，因为它的失效条件与另两个源完全不相关。

### 反推机制的实现要点

表态和回复在智信里走的是**同一条通道**——IM 的消息扩展（message expansion）：

- 表态写 `` `${emoji}_` `` 前缀的 key
- 回复写 `referInfo_` 前缀的 key
- 值是 JSON 数组，条目形如 `{ s: 账号Id, t: 时间戳 }`

所以反推只需要：遍历某条消息的全部扩展 key，收集所有 `s`，排除自己和机器人，
时间取 `t`（缺失时用 `1` 占位——动作本身证明已读，用 `0` 会被判成未读）。

**设计选择：只在展示时合并，不落盘。** 理由：

- 数据本来就在内存里，不需要额外的持久化时机
- 没有事件订阅，就没有漏订阅 / 重复订阅 / 循环依赖的风险
- **历史消息重新加载后照样生效**——落盘方案做不到这点

## 三、发送方与接收方的口径必须一致

PC 原实现有两个独立判定：

- 「这条消息要不要发回执请求」
- 「这条消息要不要登记进需回执名单」

两者各判各的，结果出现过「请求发出去了、本机却没登记、回执回来必然被丢弃」——
纯浪费，还让对方端做一次注定被丢的回执。

**教训：这两个判定必须共用同一个纯函数。**

## 四、阅读方的筛选口径，三端曾经不一致

| 端 | 阅读方回执覆盖范围 |
|---|---|
| android / ios | 按 IM SDK 的 `readReceiptInfo` 判定，**不限消息类型、不看 extra** |
| desktop（改前） | 仅 `TextMessage` / `ReferenceMessage` **且 `content.extra` 非空** |

PC 是三端里最窄的一档。而 iOS 发送方只要消息带 `mentionedInfo` 就发回执请求、不限类型——
**iOS 能发出 PC 接不住的回执请求**。本轮已把 PC 放宽到与另两端同口径。

> 反向的不对称也存在：安卓发送方只对**纯文本**发回执请求，引用消息不发
> （`ConversationFragment.java:1580` 的 `objectName.equals(TXT_MESSAGE)`），
> iOS / PC 都不限。**这条未修，需改安卓出包，单独排期。**

## 五、阅读方的触发点，三端也不一致

| 端 | 触发点 |
|---|---|
| ios | `viewWillAppear` + 退到后台 + IM 重连 + 4 处拉历史补发 |
| android | 收到回执请求事件 + 拉历史批量补发 + 进会话无条件发（私聊） |
| desktop（改前） | 群聊**只有**消息条数变化 watcher；私聊 6 个调用点但全被一道门槛拦 |

那道门槛是滚动位置状态。修的时候要注意区分两种状态：

- 「不在最新一屏」——从搜索/定位跳进会话中间时也会置位，**此时用户确实看到了消息**，不该拦
- 「下方有新消息未看到」——此时把最新消息标已读是误报，**必须拦**

原实现把两者 `||` 在一起，导致前者被误伤。**只删前者、保留后者。**

## 六、消息内容对象的构造陷阱（融云 v2 adapter 特有）

`Message.send(sourceMsg)` 内部执行 `new MessageObject(sourceMsg.content)`，
而 adapter 的构造器 `QL(messageType, objectName, content, ...)` 会把第三个参数整体塞进 `.content`。

所以调用时：

| 写法 | 结果 |
|---|---|
| `content: { 纯对象 }` | ✅ 正确 |
| `...消息实例`（展开） | ✅ 正确——实例上本来就有 `.content` 键 |
| `content: 消息实例` | ❌ **多包一层**，字段落到第二层 |

同一个文件里三种写法都出现过。新增代码统一用第一种。

## 七、可观测是刚需，不是锦上添花

本次排查最大的成本来自：**用户报问题 → 拿不到现场 → 只能读代码推断**。
三次实测（happy path、老消息、群 @某人）全部阴性，唯一有症状支撑的是「表态/回复后仍未读」。

因此实现里加了内存计数器，挂在 `window.__receiptMetrics`。
关键是要能区分这三种情况，缺一不可：

- 回执**没发出去**（阅读方筛掉了 / 被门槛拦了）
- 发了但**没收到**（窗口期 / 网络）
- 收到了但**被丢弃**（未登记 / SDK 本机记录过滤 / 名单里没这个人）

安卓 / iOS 若后续对齐，建议同样加这三类计数。

## 八、服务端已读接口：一个三端都没用起来的权威源

`datasyn/getReadMessage` 返回 `[{ accountId, msgUID, msgTimestamp, chatType, targetId, readTimestamp }]`，
接口注释明确 `chatType: 1=单聊、2=群聊`。三端**写入侧**都在打 `datasyn/readMessage`，服务端有全量数据。

但读取侧：

| 端 | 状态 |
|---|---|
| android | 接口已定义，**全仓库零调用** |
| ios | 封装已定义，**全仓库零调用** |
| desktop（改前） | 只在私聊用、`chatType: 1` 写死，且归一化时**丢掉了 `accountId`** |

这是唯一能解决「换设备已读全丢」和「三端显示不一致」的源。

> **未决**：`chatType: 2` 的返回是否真的含按人明细（同一 `msgUID` 多条不同 `accountId`）尚未实测。
> PC 侧代码已按「有明细 / 无明细」两条分支兼容，用一个 `hasPerUserDetail` 布尔做门闩——
> 无明细时群聊那半边退化为仅本地回执，**与改动前持平、不会更差**。
> 结论会在起 PC 打开任意群时由一行 console 日志给出，读到后请回填 `acceptance.md` 的「零」节。
