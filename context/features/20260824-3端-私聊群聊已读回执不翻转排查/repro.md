# 复现路径手册

> 用途：修改**前**跑一遍记录现象作基线，修改**后**再跑一遍对比。
> 每条都标了「需要什么」和「修好后应该看到什么」，按成本从低到高排。
> 对应结论编号见 `findings.md`。

## 怎么用这份手册

1. **改代码之前**，先按顺序跑一遍能跑的，把「实际看到」填进每条的表格里。这是基线。
2. 改完之后，同样的步骤再跑一遍，对照「修好后应该看到」。
3. 跑不了的（缺设备 / 缺账号）标「未测」，不要跳过不记——漏测的项在验收时最容易出事。

## R1 · 私聊老消息显示「未读」

**这条现在就能验，不用等，不用改系统时间，不需要第二个人。**

| | |
|---|---|
| 对应结论 | D2 |
| 需要 | 一台已登录的 PC，一个有 4 天以上历史的一对一聊天 |
| 耗时 | 1 分钟 |

### 为什么会这样

PC 把「谁在什么时候读了我的消息」按**发送日期分册**存在本地，一天一个文件。
但每次启动只加载 4 册：前天、昨天、今天、明天（`storeModule/index.js:38-51`）。

界面判断已读时，先看这一册在不在（`msg-list.vue:2974-2978`）：

```js
let storeReadTime =
  this.msgReadTime[data.sentDate] && this.msgReadTime[data.sentDate][data.messageUId];
let compInnerReadTime =
  this.msgReadTime[data.sentDate] && this.innerReadTime[data.messageUId];
```

**注意第二行**：连从服务端拉回来的兜底已读时间 `innerReadTime`，也被同一个「册子在不在」的条件挡着。
册子不在 → 两个都取不到 → `readTime` 为 0 → 最后走到 `return \`${statusTxt}读\``（`:3004`），
由融云本地库里的 `sentStatus` 决定显示什么。PC 重启后这个值通常是 `SENT`，于是显示「未读」。

### 步骤

1. 打开 PC 的 electronStore 目录，确认有哪些日期的册子：

```bash
ls ~/Library/Application\ Support/zhixin-test/electronStore/<你的accountId>/ | grep msgReadTime
```

（正式包把 `zhixin-test` 换成 `zhixin`；`<你的accountId>` 就是目录里那一串数字，多个账号会有多个目录）

2. 挑一个**不在「前天/昨天/今天/明天」范围内**的日期，比如今天是 8/24，就挑 8/19 的册子。
3. 打开那个册子看有几条记录（有记录才说明当时确实已读过）：

```bash
cat ~/Library/Application\ Support/zhixin-test/electronStore/<accountId>/msgReadTime-20260819.json
```

4. 在 PC 上打开对应的一对一聊天，往上翻到那一天，看**你自己发出去的**那几条消息。

### 实测记录

| 项 | 内容 |
|---|---|
| 册子日期 | |
| 册子里记录数 | |
| 界面实际显示 | |

### 判定

- **坏**：显示「未读」，但册子里明明有已读记录
- **修好后**：显示「已读」，并且带上已读时间

## R2 · 删掉本地存储，已读全部消失且回不来

| | |
|---|---|
| 对应结论 | D1、D3 |
| 需要 | 一台已登录的 PC |
| 耗时 | 5 分钟 |

### 为什么会这样

已读状态**只存在这台电脑的硬盘上**，没有任何从服务端或融云重新拉回来的路径。
换电脑、重装、清缓存，效果和手动删除完全一样。

### 步骤

1. 在 PC 上打开一个私聊和一个群聊，确认能看到「已读」和群里的「已读 N/M」。**截图存证。**
2. 完全退出 PC 客户端。
3. 备份并删除存储目录（**先备份，不然回不去**）：

```bash
cd ~/Library/Application\ Support/zhixin-test/electronStore
cp -r <accountId> <accountId>.bak
rm -rf <accountId>
```

4. 重新打开客户端，登录，打开刚才那两个会话。

### 实测记录

| 项 | 删除前 | 删除后 |
|---|---|---|
| 私聊「已读」显示 | | |
| 群聊「已读 N/M」 | | |
| 群已读入口是否还在 | | |

### 判定

- **坏**：全部变回「未读」；群聊的已读入口可能整个消失（登记表没了，`storeModule/index.js:157-159` 第一道门直接拦掉后续所有回执）
- **修好后**：进会话后能从服务端重建，恢复成删除前的样子

> 验完记得还原：`rm -rf <accountId> && mv <accountId>.bak <accountId>`

## R3 · 从搜索 / 消息定位跳进会话中间，看了但对方仍显示未读

| | |
|---|---|
| 对应结论 | A2 |
| 需要 | 两个账号（PC 一个、手机一个），一个有较长历史的一对一聊天 |
| 耗时 | 10 分钟 |

### 为什么会这样

PC 发私聊已读的入口函数 `ReadLastMessage`，开头两行就可能整个退出（`msg-list.vue:2587-2589`）：

```js
if (!this.isFirstScreen || this.showDownMsg) {
  return false;
}
```

`isFirstScreen` 表示「当前显示的是不是最新那一屏」。
从搜索结果或消息定位跳转进来时会被置为 false（`:1954`），滚动离开底部时也会（`:2298`）。

安卓进会话就无条件发（`ConversationFragment.java:1393`），iOS 在 `viewWillAppear` 就发
（`ZXRCIMBaseChatController.m:151`）——**两端都没有这道门**。

### 步骤

1. 手机（账号 B）给 PC（账号 A）发若干条消息，其中要有几条内容便于搜索的，比如「测试已读001」。
2. **A 侧不要打开这个会话**，让消息保持未读。
3. A 在 PC 上用全局搜索搜「测试已读001」，从搜索结果**跳转**进会话——这样会定位到中间，不是最新一屏。
4. A 把这段对话看完，**不要滚到底部**，直接关闭会话或切走。
5. 到手机 B 上看这几条消息的已读状态。

### 变体（同一条缺陷的另一个触发方式）

3'. A 正常打开会话，然后**往上滚**离开底部；B 此时再发一条；A 不滚回底部就切走。

### 实测记录

| 项 | 内容 |
|---|---|
| B 侧看到的状态 | |
| A 滚回底部后 B 侧是否变化 | |

### 判定

- **坏**：B 侧仍显示「未读」
- **注意**：A 滚回底部会触发补发（`isFirstScreen` 的 watcher，`:1362-1366`），所以**中途别滚到底**，否则会自愈看不出问题。这也正是这条缺陷「偶发、说不清条件」的原因。
- **修好后**：A 确实看过的消息，B 侧应显示已读

## R4 · 群里 @ 消息，PC 读了但发送方不加已读人数

| | |
|---|---|
| 对应结论 | A1 |
| 需要 | 两个账号（一个在 PC，一个在 iOS），一个共同的群 |
| 耗时 | 15 分钟 |

### 为什么会这样

PC 阅读方发回执时筛掉了大部分消息（`msg-list.vue:1433-1446`）：只处理
`TextMessage` / `ReferenceMessage`，且 `content.extra` 必须非空。

安卓 / iOS 阅读方按融云 SDK 的 `readReceiptInfo` 判定，**不限消息类型**。
而 iOS 发送方只要消息带 `mentionedInfo` 就发回执请求（`+SendMessage.m:1170`），
也不限类型——**iOS 能发出 PC 接不住的回执请求**。

### 步骤

分两组对照跑，只有这样才能区分是「PC 不回执」还是「整条链路都不通」：

| 组 | iOS 发什么 | PC 侧动作 | 看什么 |
|---|---|---|---|
| 对照组 | 群里发**纯文本** @某人（@ PC 那个账号） | 打开会话看到 | iOS 侧已读人数是否 +1 |
| 实验组 | 群里发 **@所有人**，或带 @ 的非纯文本消息 | 打开会话看到 | iOS 侧已读人数是否 +1 |

### 实测记录

| 组 | 消息类型 | iOS 侧已读人数变化 |
|---|---|---|
| 对照组 | 纯文本 @某人 | |
| 实验组 | @所有人 | |
| 实验组 | 非纯文本带 @ | |

### 判定

- **坏**：对照组 +1，实验组不变 → 坐实是 PC 阅读方的类型白名单卡住了
- **两组都不变**：说明问题更靠前（可能是 B1/B3 的登记条件），换用 R6 排查
- **修好后**：两组都 +1

> 顺带确认一下：如果实验组的「@所有人」也不通，去 PC 的开发者工具里看那条消息的 `content.extra` 有没有内容——
> 这同时能验掉 B1 和 B3（`findings.md` 第五节）。

## R5 · 安卓发「引用 + @」，谁读都不算已读

| | |
|---|---|
| 对应结论 | A3 |
| 需要 | 两个账号（一个在安卓，一个在 iOS 或 PC），一个共同的群 |
| 耗时 | 15 分钟 |

### 为什么会这样

安卓只对**纯文本**消息发回执请求（`ConversationFragment.java:1580`）：

```java
message.getObjectName().equals(IMMessageType.TXT_MESSAGE)
```

引用消息的 objectName 不是 `TXT_MESSAGE`，所以不发请求。
而安卓 / iOS 阅读方都依赖「收到过回执请求」才回执 → 没人回 → 安卓发送方永远显示未读。

### 步骤

同样两组对照：

| 组 | 安卓发什么 | 谁去读 | 看什么 |
|---|---|---|---|
| 对照组 | 群里发**纯文本** @某人 | iOS | 安卓侧已读人数 |
| 实验组 | 群里**引用一条消息 + @同一个人** | iOS | 安卓侧已读人数 |

### 实测记录

| 组 | 安卓侧已读人数变化 |
|---|---|
| 对照组 | |
| 实验组 | |

### 判定

- **坏**：对照组 +1，实验组不变
- **修好后**：两组都 +1

## R6 · PC 发的 @ 消息，隔天对方才读就不翻转

| | |
|---|---|
| 对应结论 | B4 |
| 需要 | 两个账号 + 一个共同的群；**要等一天**，或改系统时间 |
| 耗时 | 跨天 |

### 为什么会这样

PC 初始化融云 SDK 时没传参数（`IMSDKServer.js:11`），
`readReceiptTimeout` 取默认值 **1 天**（SDK 支持上限 15 天）。

SDK 内部在两个地方按这个窗口判断：写「我发过回执请求」的本机记录时，
以及收到回执响应时匹配这条记录。超窗口的回执响应会被直接丢弃，界面上就永远不翻转。

### 步骤

1. PC 在群里发一条 @ 某人的纯文本消息。**先确认当天对方读了能正常翻转**（排除其他缺陷干扰）。
2. 换一条新的 @ 消息，对方**当天不要读**。
3. 等 24 小时以上（或把对方设备系统时间往后调一天）。
4. 对方打开群看到那条消息。
5. 回 PC 看已读人数。

### 实测记录

| 项 | 内容 |
|---|---|
| 当天读（对照） | |
| 隔天读（实验） | |

### 判定

- **坏**：当天读会 +1，隔天读不变
- **修好后**：隔天读也 +1（把 `readReceiptTimeout` 提到 15 天后，至少 15 天内都应正常）

## 优先级建议

| 顺序 | 路径 | 理由 |
|---|---|---|
| 1 | **R1** | 零成本，现在就能跑，且几乎必然复现 |
| 2 | **R2** | 单人单机，能一次性暴露 D1 + D3 两条 |
| 3 | **R3** | 最贴近用户报的「私聊偶发未读」 |
| 4 | R4 | 需要 iOS 配合 |
| 5 | R5 | 需要安卓配合 |
| 6 | R6 | 要跨天，放最后 |

**R1 + R2 + R3 三条跑完，就能覆盖「显示层」的全部缺陷**，也就是同事说的 electron-store 那一块。
R4 / R5 / R6 属于「回执发送与接收」层，是另一半。

## 已知的复现盲区

- 三端融云 SDK 版本不同（安卓 5.5.3 / iOS 5.3.7 / PC v2-Adapter-5.3.3），安卓的 SDK 内部行为不可读。
  R5 如果对照组也不通，无法从代码判断是安卓 SDK 的问题还是调用层的问题，只能靠埋点。
- 服务端 `datasyn/getReadMessage` 传 `chatType: 2`（群聊）时返回什么，**尚未验证**。
  这直接决定「用服务端做权威源」的方案能不能覆盖群聊。建议在跑 R2 之前先打一发这个接口。
