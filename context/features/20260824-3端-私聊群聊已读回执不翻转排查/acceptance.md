## 零、开跑前必做：读一次服务端探测结论

代码里留了一行探测日志。PC 上打开**任意群聊**，开发者工具 Console 里找：

```
[receipt] 群已读服务端返回 条数= N 含按人明细= true/false
```

| 结论 | 含义 |
|---|---|
| `含按人明细= true` | 群已读获得可重建的权威源，换机 / 清缓存后能恢复 |
| `含按人明细= false` | 群聊那半边退化为「仅本地回执」，**与改动前持平、不会更差**。需在 status.md 记一条待办：需后端补群维度按人已读查询 |

## 一、私聊（6 条）

| # | 步骤 | 预期 | 实际 |
|---|---|---|---|
| P1 | A 在 PC 发消息给 B，B 在手机打开会话看到 | A 侧 3 秒内显示「已读」并带时间 | |
| P2 | B 在手机发消息给 A，A 在 PC 正常打开会话看到 | B 侧显示已读 | |
| P3 | **A 在 PC 用全局搜索跳进该会话中间**，看完不滚到底就切走 | B 侧显示已读（**修复重点，旧版会一直未读**） | |
| P4 | A 在 PC 往上滚离开底部，B 发新消息，A 不滚回底部 | B 侧保持未读（**不能被"修坏"**，用户确实没看到） | |
| P5 | A 翻到 5 天前自己发的消息 | 显示「已读」**且带已读时间**（旧版只有「已读」二字无时间） | |
| P6 | A 退出 PC 客户端重开，重复 P5 | 结果与 P5 一致 | |

> P3 与 P4 是一对：只删了 `!isFirstScreen`、保留了 `showDownMsg`。
> P3 过说明搜索跳转场景修好了，P4 过说明没有把「用户没看到的消息」误标已读。

## 三、表态 / 回复反推已读（5 条）—— 用户明确反馈的症状

用户原话：「大家表态、回复，还显示未读，bug 太明显了」。

这条链路**不经过融云回执通道**——表态和回复都是必须先看到消息才能做的动作，直接反推已读。
所以**即使回执全丢，这组也必须通过**。

| # | 步骤 | 预期 | 实际 |
|---|---|---|---|
| E1 | A 在 PC 群里发 @B 的消息，**B 在手机上对该消息表态**（点表情），B 不做别的 | A 侧「@B」旁小图标变已读 | |
| E2 | A 在 PC 群里发 @B 的消息，**B 在手机上回复该消息**（引用回复） | A 侧「@B」旁小图标变已读 | |
| E3 | A 在 PC 私聊发消息给 B，**B 在手机上回复该条**（引用回复） | A 侧该消息显示「已读」 | |
| E4 | **断网验证**：A 发 @B 后把 A 的网断开，B 表态，A 恢复网络重开会话 | 表态数据随扩展同步回来后，已读同样翻转 | |
| E5 | A 自己给自己的消息表态 | **不能**因此变已读 | |

> E5 是防倒退项：反推必须排除自己和机器人，否则「自己给自己点个赞就变已读」。
> 纯逻辑层已有单测覆盖（`extractExpansionReaders` 的「排除自己」「排除机器人与智能体」两条），
> 但仍需真机确认接线正确。

## 五、可观测自检（1 条）

| # | 步骤 | 预期 | 实际 |
|---|---|---|---|
| M1 | Console 执行 `window.__receiptMetrics.dump()` | 输出计数表 | |

计数含义（出问题时用来定位）：

| 计数 | 持续增长说明什么 |
|---|---|
| `privateReceiptBlocked` | 私聊回执被 `showDownMsg` 拦下——若在用户"确实看了"的场景增长，说明门槛还是紧了 |
| `groupRespEmptyForMe` | 收到群回执但 `receiptMessageDic[我]` 是空数组——**融云 SDK 的 SENT 记录本机化过滤在丢回执**，需单独排查 |
| `groupRespDroppedUnregistered` | 收到回执但该消息未登记 |
| `serverReadRowsGroup` 恒为 0 | 服务端群已读没数据，第 3 层（权威源）对群聊无效 |

## 承诺边界（汇报时不可省）

修的是代码上确定存在的缺陷，能保证**这几条路径**以后不再出问题。
但除了「表态/回复后仍显示未读」这一条，**其余缺陷都没有实测复现过**——
happy path、8/6 老消息、群 @某人 三次实测全部正常。
所以**不能断言用户遇到的就是这几条**。

配合可观测计数，发版后观察 **2 周**。若仍有反馈，让用户执行
`window.__receiptMetrics.dump()` 截图回传——计数分布能直接区分
「回执没发出去」「发了但没收到」「收到了但被丢弃」三种情况，不用再靠猜。
