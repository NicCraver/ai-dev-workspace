# Impl Notes：打开文件的下载进度与取消

> 平台无关的逻辑提炼，供其它端移植参考。最后更新：2026-08-18（iOS + web 代码完成，未真机自测）

## 问题与结论

点开一个远端文件时，原实现全程只有一个不确定态转圈（iOS `ZXProgressHUD`）。大文件下载几十秒到几分钟，用户既看不到进展也无法中止，观感等同卡死。

结论：**不需要安卓那样的独立「文件查看页」**。真正缺的是两件事——① 真实百分比；② 取消。把已有的加载浮层升级即可。

## 关键结构：底层下载点只有一个，但**上层各写各的下载编排**

进度与取消能力加在**下载层**（一个方法），这点没错；但**别以为接了下载层就自动覆盖所有入口**——这是本次踩的坑：原以为聊天文件会经过通用的「预览时按需下载」分支，实际上聊天有自己一套「先 readFile → 拿签名 → 下载 → 只把本地路径交给预览器」的编排，通用分支根本不会执行，改完后聊天文件**完全没有进度效果**。

正确做法：**逐个入口去追它自己的下载调用点**，凡是自己发起下载的地方都要接会话。

iOS 对应关系（修正后）：

| 链路 | 入口 | 谁发起下载 |
|------|------|-----------|
| AI 卡片知识来源 | `ZXAgentKnowledgeOpenLogic openItem:` | 自己调 `ZXFileClient writeToFile:progress:` |
| **聊天文件消息**（普通 / 加密 / 微应用分享） | `ZXRCIMChatLogic previewFileByModel:`（聊天页 3 个入口 + 聚合回复 3 个入口的共同收敛点） | **自己**调 `ZXFileClient writeToFile:progress:`；加密文件先走 `ZXEncryptLogic downloadTmpFile:progress:` |
| H5 文件 / 其它 | `ZXMultiMediaClient multiMediaPreviewFile:` → `openLocalFile:` | 传的是远端 URL 时才由它下载 |
| H5 知识来源 | 桥 `openKnowledgeDoc` → `openItem:` | 同第一行 |

判据：调用预览器时传的是**本地路径**（`paramsWithPath:`）说明下载已经在上层做完了，进度要加在**那个上层**；传远端 URL 才由预览器自己下载。

## 三段式进度模型

一次打开由「不确定阶段」和「可测量阶段」拼成。规则：

1. **前置阶段 0 → 8%**：元数据接口 + OSS 签名。没有真实进度，用定时器每 0.5s 前进 1%，8% 封顶（只为消除"卡住"观感，不假装快）。
2. **下载阶段 8% → 100%**：真实字节进度 `fractionCompleted`，线性映射到 `[0.08, 1.0]`。
3. **加密文件（绿盾）**：解密任务轮询沿用原有 5% → 65% 的阶段值，下载段起点改为 65%，映射到 `[0.65, 1.0]`。
4. **单调保护**：展示层只接受 `max(已展示, 新值)`，多段拼接不会回退。
5. **收尾**：到 100% 停 0.25s 再关浮层弹预览，避免"99% 突然消失"。

## 取消语义（代码审查后修正，移植时照这版）

**最重要的一条：取消也必须回调上游的 completion / handler。** 这是审查抓到的最严重缺陷——原实现取消后直接 `return`，结果：

- 上游自己的加载 HUD（进入下载前弹的那个）永远不 dismiss，界面上留一个转不完的圈；
- JSBridge 的 `responseHandler` 永不触发，web 侧 promise 永久 pending。

做法：给取消定义一个**专属错误码**（iOS = `ZXMediaPreviewCancelledCode`），取消时用它回调一次 handler；上游据此收尾但**不弹失败提示**（用户自己点的，不需要解释）。所有出口再包一层 `handleOnce` 幂等，避免成功与取消双发。


- 取消 = 会话置 `cancelled` → **中止下载任务** + **删除半成品文件** + 关浮层。
- 置位后所有在途回调（元数据、签名、下载完成、解密轮询）一律**直接丢弃**，不弹 toast（用户主动行为，无需解释）。
- **不做**断点续传 / 暂停继续 / 后台下载。下次点开重新下载。
- 解密轮询没有可中止的网络句柄，取消只能靠丢回调 + 关浮层，轮询自然结束。这点在其它端同样适用：**能 cancel 的 cancel，不能 cancel 的用状态位挡住回调**。
- **不要在取消时删目标文件**（这条最初写反了）：系统下载任务是先写临时文件、完成才 move 到目标路径。取消时目标路径要么不存在，要么是**上一次下好的完整文件**——删了等于把好缓存毁掉，下次必须重下。真正的半成品由系统自己回收。
- **取消句柄的装载时机**：下载句柄要等下载 API 返回才拿得到，而取消按钮此刻已经可点。两头都要堵：① 会话的 `onCancel` setter 发现"已经取消过"时立刻执行一次；② 拿到句柄后再查一次 `isCancelled`，是则立即 cancel。否则会出现"点了取消、界面关了、流量还在跑"。
- **并发**：取消在主线程、进度与完成在网络线程。`cancelled` / `finished` / 下载句柄都要原子，判重要加锁，否则取消后回调仍会穿透。

## 会话对象（推荐抽象）

把「浮层 + 假进度定时器 + 阶段映射 + 取消聚合」收进一个短生命周期对象，各入口只用 5 个动作：

- `start(title)`：展示浮层，启动前置假进度
- `onCancel = block`：挂中止动作（可叠加：下载 cancel + 状态回报）
- `updatePollingProgress(p)` / `updateDownloadProgress(p)`：两种阶段的进度入口
- `finish(completion)`：补到 100% 后回调（在回调里才弹预览）
- `dismiss()`：失败或不再需要

iOS 落在 `ZXFilePreviewLoadHUD.h/.m` 里的 `ZXFileLoadingSession`（**故意不新建文件**，避开 `project.pbxproj` 改动带来的排序噪声与漏加 target）。

**浮层是全局单例 → 必须做归属隔离。** 一次打开可能串起两个会话（例：解密段结束后进下载段），后开的会话会覆盖前一个的取消回调，前一个的 `dismiss` 又会把后一个的浮层一起关掉，进度还会串写到别人的浮层上。做法：浮层记一个弱引用的 `owner`，`update` / `finish` / `dismiss` 都带 owner，不匹配就不动浮层（但 `finish` 的 completion 仍要执行，否则流程断在这里）；换 owner 时把旧 owner 当作被取消处理一次，别让它的取消回调失联。

**进度未知的兜底**：服务端不给 `Content-Length` 时字节进度恒为 0。此时下载层回一个负值通知会话「退化为不确定态」，会话把假进度上限从 8% 放宽到 90% 继续缓慢爬，而不是把百分比钉死在 8%。

## 结束状态回报（给 JSBridge 用）

原生打开流程结束时回报三态之一，且**只回报一次**（用 `finishReported` 幂等）：

- `success`：预览已弹出（含外链 / 智文 Web 页 / 图片浏览器）
- `cancel`：用户点取消；**飞书 / WPS 未授权也算 cancel**（原生已拉起授权页，本次打开未完成，web 不必处理）
- `fail`：接口错误 / 签名失败 / 下载失败 / 预览失败（原生已 toast）

桥协议见 `context/bridge.md` 的 `openKnowledgeDoc`。
