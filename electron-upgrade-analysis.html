1结论摘要

  1. 阻塞点不是原生模块，是 IPC 架构——但它可以在不升级 Electron 的前提下先拆掉

    三项必改改造（ipcRenderer.sendTo 15 处、new-window 事件 9 处、@electron/remote 36 处） 全部能在 Electron 19 上完成并独立发版。这意味着升级的主要工作量可以前置、可以灰度、可以和跳版解耦。 先改架构再跳版，比"一次性升上去再修一个月"风险低一个数量级。

  2. 原生模块风险被高估：sqlite3 与 leveldown 都已是 N-API，跨 Electron 版本 ABI 稳定

    实测 node_modules/sqlite3/lib/binding/napi-v3-darwin-arm64/、leveldown@6.1.1（依赖 napi-macros + node-gyp-build）。 N-API v3 与 Node/Electron 主版本无关，不需要按 Electron 版本重编译。真正需要验证的是 Electron 21 引入的 V8 内存笼（memory cage）对外部 ArrayBuffer 的限制，而非 NODE_MODULE_VERSION。

  3. Windows 7 是唯一的战略决策点，且它是产品决策不是技术决策

    代码里有针对 Win7 的显式兜底（src/main/index.js:82 禁用硬件加速解决白屏），说明存量用户真实存在。 Electron 22 是最后一个支持 Win7/8/8.1 的主版本。不确定 Win7 用户占比之前，任何升级目标版本都是拍脑袋。 这个数字必须先拿到。

  4. macOS 签名与公证链路目前是死的，升级会强制暴露这个问题

    electron-builder.yml 中 mac.identity: "~"（跳过签名）；scripts/notarize.js 走的是 Apple 已于 2023-11 停用的 altool 路径，且未通过 afterSign 挂进构建流程——即当前 mac 包既没签名也没公证。 新版 Electron + 新版 electron-builder 对签名的强制性更高（Hardened Runtime、ASAR integrity），这条链路必须补齐。

  5. 推荐路径：先做解耦改造 → 拿 Win7 数据 → 双轨发布

    不建议"一步升到最新"，也不建议"停在 22 不动"。建议 主线跳到当前稳定版（Win10+/macOS 11+）， 同时把 Electron 22 冻结为 Win7 兼容分支只修严重缺陷——这是 VS Code / Chrome 对 Win7 长尾的通行做法。 详见第 9 节。

4Windows 7 分水岭

这是整个升级决策的分叉点，其它所有技术细节都从属于它。

4.1 事实

  • Chromium 110 起要求 Windows 10 及以上；Chromium 109 是最后一个支持 Win7/8/8.1 的版本。
  • 对应到 Electron：Electron 22（Chromium 108）是最后一个可在 Win7 上运行的主版本。Electron 23（Chromium 110）起，安装包在 Win7 上无法启动。
  • Windows 7 主流支持结束于 2015-01，扩展支持结束于 2020-01，ESU（付费扩展安全更新）也已于 2023-01 终止。

4.2 本仓库确实在服务 Win7 用户

// src/main/index.js:80-86
if (process.platform === "win32") {
  // 解决 win7 运行之后的白屏问题
  const isWin7 = os.release().startsWith("6.1");
  if (isWin7) {
    app.disableHardwareAcceleration();
  }
}

这不是防御性代码，是为解决线上已发生的问题写的兜底——说明 Win7 上有真实用户，且曾经报过白屏。 同时 electron-builder.yml 的 win 目标为 nsis / x64（ia32 已注释掉）， 说明已经放弃了 32 位 Win7。

命中的高危项只有三个：沙箱默认值（Electron 20）、new-window 移除（22）、 sendTo 移除（28）。三者全部集中在"窗口创建"与"跨窗口通信"这一个领域， 而这个领域正好就是内嵌 web 桥的实现基础。
这解释了为什么第 9 节把它们打包成一个可以先于升级独立完成的改造阶段——它们是同一件事。

6.2 electron-builder 升级链

  • 当前 23.0.3。builder 23 早于 Electron 22 发布，不认识后续版本的 fuses / ASAR integrity / 新的 mac 签名要求。
  • 档 A（Electron 22）：升到 24.x 即可，24.x 仍兼容较老的构建 Node。
  • 档 B/C：需要 25.x / 26.x，而这些版本要求构建机 Node 18+ 需查证具体下限。
  • 配置文件的组织问题：electron-builder.yml 在 .gitignore 中且属仓库提交禁忌， 意味着升级所需的 builder 配置变更（fuses、minimumSystemVersion、签名参数）没有可提交的落地位置。 需要先解决这个流程问题——例如把配置拆成"可提交的基线 + 本地覆盖层"，或改用 hook/ 中的代码路径注入 （afterPackHook.js / afterAllArtifactBuildHook.js 已是现成的可提交入口）。

7不升级的成本

7.1 安全：3 年 10 个月无补丁

  • Electron 官方只维护最新 3 个主版本。Electron 19 在 22 发布（2022-11）时即停止接收安全更新， 至今约 3 年 10 个月。
  • Chromium 102 → 140 之间累计 38 个主版本的安全修复全部缺失，其中包含多个 被野外利用的 V8 类型混淆 / 释放后使用 0-day。（具体 CVE 编号本报告不列举， 需由安全团队从 Chrome Releases 公告核对 需查证）
  • 本应用的暴露面比普通 Electron 应用更大，因为它把不受信内容加载进了高权限上下文——见 7.3。

7.2 Chromium 102 的 Web API 天花板（已经在造成实际故障）

这不是理论风险，已有实际案例：

API需要 Chrome影响
AbortSignal.timeout()103 已实际撞上——内嵌应用报 AbortSignal.timeout is not a function，功能不可用， 靠 preload polyfill 兜底

这条成本会随时间指数增长

智信 PC 端是宿主：它内嵌 web 端、行动中心、群公告、AI 框等多个独立演进的前端应用 （main-view.js:150-160 的 canUseZhixinApi 白名单）。这些应用由其它团队按现代浏览器 target 编译，它们每引入一个新 API，PC 端就多一个线上故障。
polyfill 是治标：它只能补已经撞上的，且只能补纯 JS API——CSS 特性无法 polyfill。 当前的 preload 补丁清单已有 5 项，这个清单只会变长。
换个说法：不升级 Electron 的成本，正在以"每次内嵌应用迭代都可能炸"的形式，转嫁给其它三端团队。

7.3 安全配置叠加带来的实际攻击面

把第 2.2 节的配置合起来看，main-view.js:278-283 这一档窗口同时满足：

  • nodeIntegration: true —— 页面 JS 可直接 require("child_process")
  • contextIsolation: false —— 页面与 preload 共享同一 JS 上下文，无隔离
  • webSecurity: false —— 同源策略关闭
  • 加载的是 远端 HTTP(S) URL（白名单内的内嵌 web 应用）
  • 叠加全局 ignore-certificate-errors（index.js:88）

结果：内嵌 web 应用上的任意一个 XSS，等价于 PC 端的远程代码执行； 中间人可以通过篡改被内嵌页面达到同样效果（证书校验已关）。 过时的 Chromium 让这个链条的第一环（浏览器侧漏洞）也变得更容易。

与升级的关系

升级 Electron 不会自动修复这个问题——这是应用自身的配置选择。但升级到 Electron 20+ 的 默认沙箱化会强迫团队重新审视每个窗口的权限（因为不审视就会坏），这是一次自然的收紧时机。 建议把"webSecurity: false 是否还必要"、"内嵌页是否真的需要 nodeIntegration" 作为升级改造的附带议题，而不是原样搬过去。

7.4 生态与人力成本

  • 三方 SDK 的支持窗口：融云 IM SDK 等对 Electron 19 / Chromium 102 的官方支持大概率已结束，出问题无法向厂商报障。
  • 调试工具：新版 Chrome DevTools 扩展、Vue DevTools 都不再兼容 Chromium 102，排障效率持续下降。
  • 迁移成本随时间上升：每多停留一个 Electron 版本周期，破坏性变更就多积累一层。 今天从 19 升到最新是 28-45 人天；一年后同样的跳跃只会更贵。

9分阶段实施建议

总体策略：解耦优先，不做大爆炸式升级

第 5 节的三个高危破坏性变更（沙箱、new-window、sendTo）， 其目标写法在 Electron 19 上全部可用——setWindowOpenHandler 从 12 起就有， 主进程中转从来就有，sandbox:false 显式声明在 19 上是幂等的。
这意味着可以先把代码改成"两个版本都能跑"的形态，在 Electron 19 上正常发版验证， 等改造稳定后再单独跳版。跳版那一步的 diff 就只剩 package.json 的版本号和工具链， 出问题时二分定位成本极低。

阶段 0 · 决策输入收集　约 3–5 人天，可与阶段 1 并行
  • 埋点统计 Win7/8.1 客户端占比与 macOS 版本分布（这是唯一的阻塞项，没有它无法定目标版本）
  • 向融云确认 IM SDK 对新版 Electron/Chromium 的支持矩阵
  • 核查 Windows 签名证书到期日与续期方式；申请 App Store Connect API Key（公证用）
  • 确认崩溃上报服务 192.168.5.55:33855 是否仍在运行
  • 建立性能基线：当前版本的启动耗时、常驻内存、崩溃率——升级后要对比

出口条件：拿到 Win7 占比，据此在第 4.4 节三种策略中选定一种。

阶段 1 · 前置清理　约 2–3 人天
  • 统一依赖锁文件：删掉 yarn.lock 或 package-lock.json 之一；把 leveldown 的声明版本对齐到实装的 6.1.1（R13）
  • 删除死配置：enableRemoteModule（config/index.js:37）、 enableBlinkFeatures（:41）、注释掉的 electron-updater 模板代码（index.js:452-469）
  • 解决 electron-builder.yml 的可提交性问题——升级需要的配置变更必须有落地位置（见 6.2）
  • 为 trigger-result 跨窗口通道补冒烟测试（当前 test/unit 几乎空置）
阶段 2 · 架构解耦改造（仍在 Electron 19 上）　约 8–12 人天

本阶段每一项都可独立发版验证，这是整个方案降低风险的核心。

  1. new-window → setWindowOpenHandler（9 处）。 以 webview-control.vue:208 为模板。main-view.js:342 的 event.newGuest 模式需重构为 overrideBrowserWindowOptions + did-create-window。
  2. ipcRenderer.sendTo → 主进程中转（15 处）。 新增 ipc/relay-ipc.js；保持 window.webview 对外接口签名不变，只换内部实现， 这样 web 端不需要改。同步 context/bridge.md。
  3. 显式化沙箱设置：所有 BrowserWindow 与 <webview> 补上显式 sandbox: false（或对 webview 用 nodeintegration）， 让 Electron 20 的默认值变化不再影响本应用。这一步在 19 上是幂等的，零行为变化，但把 R1 提前消除。
  4. （可选，建议）preload 的 contextBridge 化——若时间不够可推迟到升级后， 但需明确记为技术债。

出口条件：上述改造在 Electron 19 上完整发版并观察一个迭代周期，崩溃率无恶化。

阶段 3 · 工具链升级　约 4–6 人天
  • 构建 Node：14.21.3 → 目标版本（按选定档位）。同步更新 package.json#volta。
  • 加 NODE_OPTIONS=--openssl-legacy-provider 绕过 webpack 4 md4 问题（R11）。
  • electron-builder 升级；验证 Windows 签名与 NSIS 产物。
  • 补齐 macOS 签名 + 公证：electron-notarize → @electron/notarize 2.x， altool → notarytool，electron-builder.yml 补 afterSign 与真实 mac.identity。此项可与其它工作并行，不占关键路径（R5）。
  • electron-rebuild → @electron/rebuild（低优先，N-API 下需求不大）。

出口条件：在不改 Electron 版本的前提下，新工具链能完整打出 win/mac 包并正常启动。

阶段 4 · Electron 跳版　约 6–12 人天（按档位）

到这一步，代码 diff 理想情况下只有 package.json 里的 electron 版本号。

  1. 第一件事：最小 demo 验证 V8 内存笼与原生模块（R3）——sqlite3 读写 + leveldb 读写压测。 这一项若失败，整个升级要回到依赖层重新规划，必须最先做。
  2. 逐档验证：若选双轨，先出 legacy/electron-22 分支的 Win7 包并冻结；主线再跳目标版本。
  3. 回归清单按第 3.1 节"回归范围"逐项执行。重点：内嵌 web 桥全通道、多窗口互通、截图两套实现、 WPS/飞书授权页、转发弹窗。
  4. 对比阶段 0 采集的性能基线。
阶段 5 · 灰度发布　约 2–4 周日历时间
  • 利用现有的 gray 环境（MODE_ENV=gray，已有 build:gray / pack:*-gray）做内部灰度。
  • 升级源按 os.release() 分流：Win7 客户端只推 legacy 包（R6）。
  • 监控指标：崩溃率、启动成功率、内嵌 web 页面加载失败率、IM 消息收发成功率。
  • 准备回滚方案：保留上一版本安装包与升级源开关。

理由三条：

  1. 只有当前稳定版能持续拿到安全补丁。Electron 只维护最新 3 个主版本，升到 22 或 32 都是把同一笔钱付两遍。
  2. 阶段 2 的解耦改造把大部分风险前置了。三个高危变更都能在 Electron 19 上先改先验证， 真正的跳版风险被压缩到"原生模块 + Chromium 渲染回归"两项，都是可测的。
  3. 双轨的增量成本（8–10 人天）远低于它消除的不确定性。它把"Win7 占比"从一个阻塞决策的问题 降级成一个可以慢慢收敛的运营问题——不必等 IT 换完机才能动升级。

唯一的前置条件：阶段 0 必须先拿到 Win7 占比数据。若该数字 <1%，直接砍掉双轨， 总量降到 40–55 人天。

建议不要捆进本次升级的三件事

它们各自都是大工程，捆在一起会让问题无法二分定位：

  • webpack 4 → 5（用 --openssl-legacy-provider 先绕过）
  • Vue 2 → 3（与 Electron 版本无耦合）
  • @electron/remote 完全移除（升到 2.1.x 即可满足升级需求；36 处收敛单独排期）
